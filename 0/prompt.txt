# Phase 4 Agent Registry

## Summary

Implement the authoritative Phase 4 agent registry as a PostgreSQL-backed Go application API. It will accept compiled manifest bytes, reuse `manifest.Read` for closed validation and RFC 8785 canonicalization, store immutable versions, and retrieve exact canonical manifests by `(name, version)` or digest.

No gRPC/HTTP server, provider adapter, workflow integration, Python runtime, or new manifest wire format is included. The Phase 3 provider recommendation will be corrected to match the authoritative roadmap: Phase 4 is the registry, Phase 5 is the fake reasoning gateway, and a real provider remains Phase 10.

The live baseline is clean: `make check` passes with 47 Python tests, and `make integration-test` passes against disposable PostgreSQL.

## Thin Vertical Slices

1. `phase04/registry-registration`
   - Add `go/internal/registry` with a PostgreSQL-backed registration application boundary.
   - Extract the existing advisory-lock/digest-ledger migration mechanics into a small shared internal migration helper; retain workflow migration behavior and give the registry its own checked-in `0006` migration.
   - Add `agent_registrations` with identity, digest, canonical manifest bytes, and registration timestamp.
   - Validate and canonicalize input exclusively through `manifest.Read`; invalid manifests produce no database write.
   - Persist a valid manifest and return the stored canonical record.

2. `phase04/immutable-versions`
   - Make `(agent_name, agent_version)` the immutable identity and the manifest digest unique.
   - Make exact duplicate registration idempotent, returning the existing record with `Created=false`.
   - Return `ErrVersionConflict` when the same identity is presented with different canonical content.
   - Add database enforcement rejecting `UPDATE` and `DELETE`, so immutability does not depend only on application code.

3. `phase04/identity-lookup`
   - Add lookup by exact agent name and semantic version.
   - Return `ErrNotFound` for an absent identity and `ErrInvalidArgument` for malformed lookup keys.
   - Re-read stored canonical bytes through `manifest.Read` and verify that the calculated digest and embedded identity match the database columns before returning them.

4. `phase04/digest-lookup`
   - Add lookup by lowercase SHA-256 digest.
   - Reject malformed digests before querying.
   - Return the same canonical record shape as identity lookup, preserving exact registered bytes and registration metadata.

5. `phase04/registry-hardening`
   - Prove concurrent identical registration converges on one row and concurrent conflicting registration produces one winner plus deterministic conflicts.
   - Prove migration replay, migration-digest protection, database immutability, failed-registration rollback, and lookup integrity.
   - Extend `make integration-test` to run both workflow and registry suites against the disposable PostgreSQL instance without relying on package execution order.
   - Update architecture, security, resource analysis, agent-manifest documentation, decision log, development instructions, and a Phase 4 completion report. Correct the stale Phase 3 next-phase recommendation.

## Go Interfaces

```go
type Registry struct { /* PostgreSQL pool */ }

func New(pool *pgxpool.Pool) *Registry
func Migrate(ctx context.Context, connectionString string) error

func (r *Registry) Register(
    ctx context.Context,
    rawManifest []byte,
) (RegisterResult, error)

func (r *Registry) Get(
    ctx context.Context,
    name string,
    version string,
) (Record, error)

func (r *Registry) GetByDigest(
    ctx context.Context,
    digest string,
) (Record, error)
```

`Record` contains the validated `manifest.Manifest`, a defensive copy of its exact canonical JSON, lowercase digest, and registration timestamp. `RegisterResult` contains the record plus `Created`. Stable sentinel errors distinguish invalid arguments/manifests, version conflicts, missing registrations, and corrupt persisted data.

## Test and Acceptance Plan

- Unit tests: invalid/unknown manifest fields, unsafe policies, malformed identities and digests, canonicalization drift, error classification, and defensive byte ownership.
- PostgreSQL tests: first registration, exact replay, conflicting replacement, identity lookup, digest lookup, missing lookup, update/delete rejection, concurrent identical/conflicting calls, and migration replay/digest checks.
- Every stack branch must pass `make check`; database-affecting branches must also pass `make integration-test`.

Acceptance requires idempotent identical registration, rejection of conflicting version replacement, exact retrieval through both lookup paths, and database-enforced immutability.
